# Risk Log

## R-024 — Неполная загрузка исходников

**Статус:** контролируется автоматически.

Контроль: workflow `Repository integrity` завершает проверку с ошибкой при отсутствии обязательных компонентов.

## R-025 — Небезопасная production-конфигурация

**Статус:** снижен startup gate.

Риск: приложение может быть запущено в production с HTTP, небезопасной cookie, коротким стандартным admin token, относительной SQLite-базой или общим каталогом для storage и backup.

Контроль: `scripts/check_config.py` вызывается Docker entrypoint до миграций. При `APP_ENV=production` обнаруженная небезопасная настройка завершает запуск с кодом ошибки.

Остаточный риск: проверка конфигурации не заменяет внешний secret manager, TLS termination, ограничение сетевого доступа и ротацию секретов.

## R-026 — Утечка приватных данных через публичный GitHub

**Статус:** снижен CI privacy gate без VIN allowlist.

Риск: случайный commit `.env`, SQLite-базы, credential-файла, токена, приватного ключа или реального VIN делает данные доступными в истории публичного репозитория.

Контроль: `scripts/check_repository_privacy.py` проверяет обязательную структуру, запрещённые файлы и расширения, известные форматы секретов и возможные 17-значные VIN до миграций и тестов. Публичные test/seed fixtures используют демонстрационные идентификаторы и не исключаются по пути.

Остаточный риск: pattern scan не гарантирует обнаружение всех видов секретов и не удаляет данные из уже опубликованной Git history; при реальной утечке необходимы немедленная ротация и очистка истории.

## R-027 — Неограниченный рост storage владельца

**Статус:** снижен owner-wide quota.

Риск: владелец может загрузить неограниченное число документов через события и сервисные визиты, исчерпав диск приложения или ухудшив время backup/restore.

Контроль: SQLAlchemy listener проверяет количество и суммарный объём активных вложений по всем автомобилям владельца до вставки Attachment. Лимиты задаются `MAX_OWNER_ATTACHMENTS` и `MAX_OWNER_STORAGE_BYTES`; превышение возвращает структурированные HTTP 409/413 ошибки.

Остаточный риск: физический storage остаётся локальным, отсутствуют резервирование дискового пространства и per-plan quotas.

## R-028 — Расхождение квоты и отображаемого usage

**Статус:** снижен единым read model, API и owner UI.

Риск: если enforcement, API и интерфейс используют разные правила, владелец может видеть неверный остаток квоты.

Контроль: `storage_usage_for_owner` используется как единый источник расчёта для listener, сервиса `owner_storage_usage` и аутентифицированного `GET /api/me/storage`. Owner UI отображает серверные значения без самостоятельного пересчёта, обновляется после удаления и показывает предупреждения при 80%/95%.

Остаточный риск: конкурентные загрузки в многопроцессном deployment могут одновременно пройти предварительную проверку до фиксации соседней транзакции.

## R-029 — Потеря PWA-артефактов из-за плоской загрузки

**Статус:** устранён восстановлением `app/static` и тестом структуры.

Риск: FastAPI монтирует `app/static`, поэтому наличие одноимённых файлов только в корне репозитория приводит к ошибкам `/`, manifest, offline shell и service worker.

Контроль: все текстовые и бинарные PWA-артефакты восстановлены внутри `app/static`; `tests/test_storage_ui.py` проверяет обязательный набор файлов.

## R-030 — Неограниченное создание публичных ссылок

**Статус:** снижен owner-wide и per-vehicle quota.

Риск: владелец может создавать неограниченное количество временных ссылок по множеству автомобилей, увеличивая поверхность публичного доступа и объём исторических записей.

Контроль: SQLAlchemy listener считает только активные, неотозванные и неистёкшие ShareLink. Лимиты задаются `MAX_ACTIVE_SHARE_LINKS_PER_VEHICLE` и `MAX_ACTIVE_SHARE_LINKS_PER_OWNER`; превышение возвращает структурированный HTTP 409.

Остаточный риск: конкурентные вставки в многопроцессном deployment могут одновременно пройти предварительный count; для production после SQLite потребуется транзакционный или атомарный счётчик.

## R-031 — Устаревшее отображение public share usage

**Статус:** снижен принудительным обновлением UI.

Риск: владелец может видеть старое число активных ссылок после создания или ошибки quota и повторять заведомо невозможную операцию.

Контроль: owner UI загружает `GET /api/me/shares` при восстановлении сессии, по кнопке обновления и после каждой успешной или неуспешной попытки создания ссылки. Ошибки лимита преобразуются в понятные сообщения.

Остаточный риск: истечение ссылки происходит по времени без push-события; до ручного обновления или следующей операции карточка может показывать значение, рассчитанное до истечения.

## R-032 — Владелец не может определить и немедленно отозвать действующий публичный доступ

**Статус:** снижен owner-scoped списком и revoke UI.

Риск: агрегированное число ссылок не показывает, к какому автомобилю относится публичный доступ и когда он завершится; без явного отзыва владелец вынужден ждать истечения или создавать новую ссылку.

Контроль: `GET /api/me/shares/list` возвращает только действующие ссылки текущего владельца с автомобилем, `expires_at` и `seconds_remaining`. UI вызывает защищённый `DELETE /api/share/{share_id}` и после успеха перечитывает список и usage.

Остаточный риск: оставшееся время уменьшается на клиенте только после обновления; realtime countdown и push-синхронизация не входят в MVP.

## R-033 — Физический storage расходится с Attachment records

**Статус:** снижен fail-closed retention cleanup.

Риск: soft-deleted файлы продолжают занимать диск и попадать в backup; orphan-файлы не учитываются квотой; пропавший активный файл означает потерю доказательства. Небезопасное автоматическое удаление может уничтожить действующий документ.

Контроль: `scripts/cleanup_attachments.py` выполняет dry-run по умолчанию, сверяет все Attachment records с `STORAGE_PATH`, защищает активные файлы независимо от возраста, удаляет только старые soft-deleted и orphan-файлы, повторно проверяет eligibility перед unlink и записывает атомарный JSON audit report. Apply полностью блокируется при пропавшем активном файле, небезопасном пути, symlink, soft-delete без `deleted_at` или повторном появлении purged-файла. Успешное физическое удаление фиксируется `purged_at` и `purge_reason`.

Остаточный риск: файловая операция и SQLite commit не являются одной атомарной транзакцией. При аварии между unlink и commit возможна запись `soft_deleted_file_missing` на следующем запуске; audit report и fail-closed scan позволяют обнаружить ситуацию, но не восстанавливают файл без backup.

## R-034 — Релиз объявлен без единого проверяемого результата

**Статус:** устранён для release candidate; продолжает контролироваться для каждого релиза.

Риск: отдельные CI-команды могут быть выполнены для разных состояний репозитория, а пустой commit status не позволяет доказать, что миграции, полный pytest, maintenance CLI и Docker validation прошли вместе.

Контроль: `scripts/release_check.py` запускает восемь release gates последовательно для одного checkout, собирает коды возврата, длительность и ограниченный stdout/stderr каждого шага в JSON. GitHub Actions публикует отчёт `autopassport-release-check` при любом результате. Для предрелизного `main` подтверждены `passed=true`, пустой `failed_steps`, 8/8 gates и 70 тестов.

Остаточный риск: версия `0.25.0` считается окончательно выпущенной только после зелёного отчёта для её merge commit и controlled deployment smoke test.

## R-035 — Release runner завершается до создания отчёта

**Статус:** снижен перехватом инфраструктурных ошибок и timeout.

Риск: отсутствующая команда, системная ошибка запуска subprocess или зависший pytest/Docker могли выбросить исключение внутри orchestrator. В этом случае GitHub Actions переходил к публикации artifact, но JSON-файл отсутствовал, поэтому диагностика release candidate терялась.

Контроль: каждый `CheckStep` имеет явный timeout. `FileNotFoundError` и другие `OSError` записываются как failed result с кодом 127; `TimeoutExpired` — с кодом 124 и доступным частичным stdout/stderr. Остальные шаги продолжают выполняться, после чего создаётся единый JSON report.

Остаточный риск: аварийное завершение Python-процесса или невозможность финальной записи могут оставить только bootstrap-report.

## R-036 — CI падает до запуска release runner

**Статус:** снижен bootstrap artifact.

Риск: сбой `actions/setup-python`, установки зависимостей или раннего workflow step происходит до создания отчёта `scripts/release_check.py`. Ранее publish step с `if: always()` не имел файла для загрузки и observability терялась полностью.

Контроль: сразу после checkout workflow создаёт валидный `data/reports/release-check.json` со статусом `bootstrap`, `passed=false` и failed step `workflow_before_release_runner`. Полный release runner заменяет этот файл; если ранний сбой сохраняется, artifact всё равно показывает точную границу отказа. Статические тесты проверяют порядок bootstrap → install → release и обязательную публикацию artifact.

Остаточный риск: сбой checkout или самого artifact upload action остаётся вне контроля репозитория.

## R-037 — GitHub Actions результат невидим через Commit Status API

**Статус:** снижен явной публикацией commit status.

Риск: GitHub Actions создаёт check runs, тогда как используемый канал диагностики может читать только legacy commit statuses. Пустой список statuses в этом случае ошибочно воспринимается как отсутствие запуска или результата.

Контроль: workflow получил `statuses: write` и через `actions/github-script` всегда публикует context `autopassport/release-check`. Состояние `success` допускается только при `report.passed === true` и пустом `failed_steps`; bootstrap, отсутствующий или неуспешный отчёт публикуются как `failure`. `target_url` ведёт на конкретный workflow run.

Остаточный риск: если workflow не стартовал, checkout не выполнен или GitHub запрещает запись статуса политикой репозитория, context не появится; JSON artifact и workflow logs остаются дополнительными источниками диагностики.

## R-038 — Расхождение номера версии между runtime, OpenAPI и PWA

**Статус:** снижен каноническим `VERSION` и release tests.

Риск: файл релиза может содержать `0.25.0`, пока `/health`, OpenAPI или cache name остаются на предыдущей версии/RC. Это затрудняет диагностику развертывания и может оставить установленному PWA устаревший shell.

Контроль: `app/main.py` читает `VERSION`, задаёт `app.version` и единый `/health`; тест проверяет runtime и файл. PWA cache identifier меняется в release commit, а README проверяется repository integrity workflow.

Остаточный риск: PWA cache name пока обновляется вручную и должен оставаться частью обязательного release checklist до автоматической генерации build metadata.

## R-039 — Документ загружен в паспорт не того автомобиля

**Статус:** снижен явным контекстом выбранного автомобиля.

Риск: при нескольких автомобилях владелец мог открыть экран «Скан» и выбрать файл, не видя, какой `vehicleId` используется для загрузки.

Контроль: экран до выбора файла показывает марку, модель, маскированный VIN, год и пробег; загрузка отключена без выбранного автомобиля; действие «Сменить» возвращает в гараж к активной карточке. Backend продолжает проверять owner/vehicle boundary.

Остаточный риск: сценарий ещё не проверен на физическом телефоне с двумя реальными автомобилями и медленным соединением.
