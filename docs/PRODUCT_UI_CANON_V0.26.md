# AutoPassport v0.26 — канонический продуктовый UX

Статус: утверждённый UX-контракт для канонической ветки БИ AutoPassport.

## 1. Назначение

AutoPassport должен восприниматься как мобильное приложение для ведения доказуемой истории автомобиля, а не как административная панель или набор HTML-форм.

Основной пользовательский результат:

```text
Документ или действие владельца
→ понятный черновик
→ проверка владельцем
→ подтверждённая запись
→ обновлённая история и паспорт автомобиля
```

## 2. Визуальный канон

Приложение строится вокруг одного автомобиля и крупных сценарных карточек.

Обязательные признаки:

- мобильная ширина и safe-area для PWA;
- верхняя панель AutoPassport;
- крупная карточка выбранного автомобиля;
- быстрые действия без раскрытия длинных форм;
- архив автомобиля в виде карточек разделов;
- последняя запись на главном экране;
- фиксированная нижняя навигация;
- формы доступны только как fallback внутри отдельного сценария;
- реальные данные не заменяются демонстрационными значениями.

Нижняя навигация v0.26:

```text
Главная | История | Скан | Паспорт
```

## 3. Главный экран

Главный экран обязан отвечать на четыре вопроса без переходов:

1. Какой автомобиль выбран?
2. Какой у него текущий пробег?
3. Что было добавлено последним?
4. Как быстро добавить новый документ или запись?

Минимальные блоки:

- карточка автомобиля;
- быстрые действия: пробег, новая запись, поделиться;
- состояние архива: ремонты, детали, пробег, документы;
- последняя подтверждённая запись;
- предупреждения только на основании фактических данных владельца.

Запрещено:

- показывать фиктивную рекомендацию как факт;
- автоматически диагностировать неисправность;
- выводить полный VIN на публичном или обзорном экране;
- превращать главный экран в форму создания записи.

## 4. Канонический сценарий «Сканировать документ»

Поддерживаемые входы:

- фотография чека;
- PDF или фотография заказ-наряда;
- акт выполненных работ;
- диагностический отчёт;
- смета;
- текст, вставленный владельцем.

Целевой поток:

```text
Выбор автомобиля
→ фотографирование или загрузка файла
→ проверка формата и размера
→ сохранение исходного документа
→ извлечение текста
→ структурированный AI-черновик
→ экран проверки
→ ручное подтверждение
→ создание или обновление ремонтного визита
→ привязка исходного документа к визиту
```

Ни OCR, ни AI не имеют права напрямую записывать данные в подтверждённую историю.

## 5. Document Inbox

До AI-парсера документ должен иметь самостоятельный жизненный цикл.

Минимальные статусы:

```text
uploaded
processing
needs_review
confirmed
failed
```

Минимальные связи:

- владелец;
- автомобиль;
- исходный файл;
- тип документа;
- необязательный ремонтный визит;
- результат распознавания;
- подтверждённый пользовательский результат.

Документ без подтверждения не повышает доверие записи и не создаёт ремонт автоматически.

## 6. Экран проверки AI-черновика

На одном экране пользователь должен видеть:

- автомобиль;
- тип документа;
- дату;
- пробег;
- сервис или исполнителя;
- тип визита;
- перечень работ;
- перечень деталей и материалов;
- суммы по позициям;
- итоговую сумму;
- исходный документ;
- поля, в которых распознавание не уверено.

Действия:

```text
Исправить
Сохранить черновик
Подтвердить и внести в историю
Удалить черновик
```

Кнопка подтверждения должна явно сообщать, что запись попадёт в историю автомобиля.

## 7. Trust-модель

Источник данных отображается явно:

- заявлено владельцем;
- извлечено из документа и не подтверждено;
- подтверждено владельцем;
- подтверждено приложенным документом.

AI-уверенность не равна уровню доверия записи.

## 8. UX-ограничения

- Не показывать более одного основного действия на экране как primary.
- Не требовать повторного ввода данных, найденных в документе.
- Не скрывать исходный документ после распознавания.
- Не удалять документ при ошибке AI-парсера.
- Не создавать визит без выбранного автомобиля.
- Не использовать alert как основной интерфейс подтверждения в финальном UX.
- Не добавлять новые длинные формы на главный экран.

## 9. Definition of Done для v0.26 Mobile App Shell

Инкремент считается завершённым, если:

- после входа открывается главный экран приложения, а не форма;
- выбранный автомобиль отображается карточкой;
- нижняя навигация переключает отдельные экраны;
- формы создания спрятаны внутри сценария «Добавление»;
- экран «Скан» открывает камеру или выбор файла;
- выбранный файл проходит клиентскую проверку формата и размера;
- интерфейс честно сообщает, что AI ещё не выполнен, если backend отсутствует;
- существующие операции с автомобилем, историей, PDF и публичной ссылкой не сломаны;
- release-check для commit SHA завершён успешно.

## 10. Следующие проверяемые инкременты

### UX-026-02 — Scan intake

- выбор автомобиля обязателен;
- камера/файл принимают JPEG, PNG, PDF;
- файл валидируется до отправки;
- отображаются имя, тип и размер;
- пользователь выбирает тип документа;
- создаётся upload-запись без AI-разбора.

### DATA-027-01 — Document Inbox model

- отдельная таблица входящих документов;
- миграция Alembic;
- owner/vehicle boundary;
- статусы обработки;
- API create/list/detail/delete;
- тесты доступа и жизненного цикла.

### AI-028-01 — Text draft parser

- первым входом является вставленный текст;
- результат строго структурирован;
- обязательна схема валидации;
- ничего не сохраняется в историю без подтверждения;
- сырой ответ модели не является источником истины.

### AI-028-02 — Image/PDF extraction

- OCR или vision-извлечение;
- сохранение исходного файла;
- диагностируемые ошибки;
- повторный запуск без дублирования документа.

## 11. Каноническое решение

Любая следующая итерация AutoPassport должна проверяться против этого документа. Изменения, которые возвращают главный экран к набору полей, добавляют фиктивные рекомендации или записывают AI-результат без подтверждения, считаются регрессией продукта.
