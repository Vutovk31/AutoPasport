## Визуальные решения

- mobile-first shell для ширины 320–430 px;
- одна основная задача экрана — добавить или проверить документы;
- нижняя навигация с иконками и подписями;
- минимальная форма загрузки: тип документа + файл;
- зоны нажатия не менее 44–48 px;
- статусы документа показаны понятными пользовательскими формулировками;
- предупреждение об отсутствии автоматического изменения истории вынесено в первый экран;
- предусмотрены loading, empty, failed и offline состояния.

## Использованные API

- `GET /api/vehicles/{vehicle_id}/documents`
- `POST /api/vehicles/{vehicle_id}/documents`

Поля ответа используются строго по действующему контракту: `id`, `vehicle_id`, `linked_visit_id`, `document_type`, `original_name`, `media_type`, `size_bytes`, `sha256`, `status`, `failure_reason`, `created_at`, `updated_at`.

## Доступность и адаптивность

- semantic landmarks и `aria-label` для навигации;
- `aria-live` для динамических состояний;
- `role=status` для offline и ошибок формы;
- modal sheet имеет `role=dialog`, `aria-modal=true`, закрытие по Escape и возврат фокуса;
- текст и имена файлов допускают перенос без горизонтального скролла;
- CSS-ограничения рассчитаны на 320–430 px.

## Фактически выполненные проверки

- статический frontend contract-тест для GET/POST Document Inbox;
- проверка multipart-полей `document_type` и `file`;
- проверка отсутствия обещаний OCR и автоматического создания визита;
- проверка наличия mobile/accessibility guards;
- ручная сверка полей и статусов с `app/document_inbox_api.py` из `main`.

## Непроверенные элементы

- визуальная регрессия в реальном Safari iOS и Chrome Android;
- реальная загрузка файла через авторизованную сессию;
- поведение backend parser runtime после загрузки;
- переход на экран проверки draft, поскольку маршрут интеграции shell в текущем задании не определён.

## Необходимые backend-контракты

Для следующего инкремента нужен подтверждённый маршрут получения списка автомобилей пользователя или явный способ передачи `vehicle_id` из текущей карточки автомобиля. Frontend не имитирует автомобиль и ожидает `vehicle_id` в query string.

Для экрана проверки распознанных данных существующего `GET /api/documents/{document_id}/draft` достаточно для чтения draft. Для навигации из Inbox необходимо согласовать, какой статус документа гарантирует наличие draft и какой URL страницы считается каноническим.

## Инструкции интегратору

1. Проверить commit в `agent/mve-ui` и не переносить изменения прямым копированием без contract-тестов.
2. Подключить `app/static/mve/index.html` к согласованному frontend route или static mount.
3. Передавать реальный `vehicle_id` при открытии: `?vehicle_id=<id>`.
4. Запустить `pytest tests/test_mve_document_inbox_contract.py`.
5. Выполнить smoke-тест авторизованного GET/POST Document Inbox.
6. Merge в `main` выполняет только канонический PM/CTO-чат.
